# ============================================================================
# Audtheia V2 desktop dependencies
#
# This list grows incrementally as each component is built. Do not add a
# package speculatively. Add it only when a module actually imports it, and
# pin its version against the current PyPI release verified at build time
# rather than asserting a fast-moving version number from memory.
#
# These are the desktop hub's runtime dependencies. Field-station-only packages
# (the accelerator runtime, the camera stack, the acoustic model libraries) are
# installed on the Raspberry Pi by the Pi setup path, not from this file, so the
# desktop install stays small and the two device roles do not drag in each
# other's hardware libraries.
# ============================================================================

# The storage layer (schema.sql, database.py) uses only Python's built-in
# sqlite3 and uuid modules, so no third-party dependency is required for it.

# --- Active dependencies (pinned against a live PyPI check at build time) ---

# reports/generate.py: PDF output. Pure Python with no compiled extension, so it
# installs and runs the same on Windows and on Raspberry Pi OS Bookworm 64-bit,
# and it stays behind an import seam so the report module still loads and still
# writes CSV when it is absent. The CSV output itself needs only the standard
# library.
fpdf2==2.8.7

# app/server.py: the local desktop web backend. FastAPI defines the endpoints
# and uvicorn serves them on the loopback address; both are pure Python wheels
# that install the same on Windows and Raspberry Pi OS Bookworm 64-bit. The
# module imports the framework inside its application factory, so importing the
# file needs neither package; only building or running the server does.
fastapi==0.139.0
uvicorn==0.50.0

# starlette is the framework FastAPI serves through. FastAPI accepts a range of
# starlette versions, so it is pinned here to the exact version this release is
# built and tested against, which keeps a fresh install reproducible instead of
# letting it drift to a newer starlette that expects a different HTTP client.
# Pure Python wheel, identical on both platforms.
starlette==1.3.1

# analysis/verify.py: desktop RF-DETR verification through ONNX Runtime. The
# verifier is injected, so verify.py itself imports nothing here; this is the
# runtime the desktop adapter loads to score the ONNX model. The wheel ships for
# Windows (amd64) and Linux aarch64 (Raspberry Pi OS Bookworm 64-bit), so one
# pin covers both roles a desktop hub can run on. Its wheels require Python 3.11
# or newer, which the setup bootstrap checks before installing.
onnxruntime==1.27.0

# analysis/dream.py: the desktop-only generative model, run through llama.cpp.
# This project publishes no prebuilt wheels on PyPI, so a plain install compiles
# it from source and needs a C++ toolchain. The setup bootstrap installs this
# pin from the maintainer's prebuilt CPU wheel index instead, and treats a
# failure as non-fatal so the rest of the desktop still installs and runs; the
# longitudinal pass simply waits until the model runtime is present. On the
# Raspberry Pi its aarch64 wheel comes from the system's own wheel index.
llama-cpp-python==0.3.32

# scripts/fetch-species-data: the per-species occurrence and conservation fetch
# talks to the GBIF and IUCN web APIs over HTTPS under the operator's own
# credentials. Pure Python wheel, identical on both platforms.
requests==2.34.2

# --- Desktop capture and tracking (a station with no field hardware) ---
# These let the desktop run the full detection pipeline against an ordinary
# webcam, a network stream, or a video file, with the screening model run through
# ONNX Runtime, so the platform is usable with no Raspberry Pi present. The
# detection loop imports numpy and Pillow directly, the desktop capture drivers
# add OpenCV for video, and supervision provides the ByteTrack tracker that turns
# per-frame detections into one track per animal. onnxruntime is already pinned
# above and doubles as the desktop detector runtime. These ship wheels for Windows
# amd64 and Raspberry Pi OS aarch64, pinned to the same numpy the tests and the
# field tier use.
#
# OpenCV is the full build rather than the headless one because supervision
# requires the full opencv-python distribution; using it here keeps a single,
# consistent OpenCV on the desktop instead of two builds that would clash. On a
# desktop with no graphical environment the full build wants the system OpenGL
# library (libGL), which a personal computer with a display already has.
numpy==2.4.6
pillow==12.3.0
opencv-python==5.0.0.93

# supervision: the ByteTrack multi-object tracker the detection loop uses to
# aggregate per-frame detections into one event per animal, so the desktop
# hardware-free capture path tracks exactly as a field station does. It is a
# pure-Python wheel that pulls matplotlib, scipy, and opencv-python as
# dependencies, all of which ship wheels for Windows amd64 and Raspberry Pi OS
# aarch64. Note for Windows: some antivirus tools raise a heuristic false positive
# on one compiled matplotlib file (ft2font); it is a known false alarm on a
# legitimate library, and the setup notes explain how to allow it.
supervision==0.29.0

# yt-dlp resolves a web-page video address (a YouTube or Pixcams live page, for
# example) down to the direct stream address that OpenCV then reads, so a desktop
# station can watch a public wildlife livestream with no field hardware. It is
# used only for a source given as "stream:<page-address>"; a direct camera, file,
# or stream URL never needs it. Pure Python, identical on both platforms. This is
# the one dependency that benefits from periodic updates, since it tracks changes
# on the sites it reads.
yt-dlp==2026.7.4

# tzdata: Windows does not ship the IANA time-zone database, so a station whose
# display time zone is set to a named zone (for example "America/Puerto_Rico"
# rather than the default "auto") needs this package to resolve it. Pure data
# package, identical on every platform.
tzdata==2026.2

# Built-in verification suite: the interface checks drive the app through
# fastapi's TestClient. The pinned starlette above uses the httpx2 client, and
# httpx is kept alongside it for the other checks. Both are pure-Python wheels,
# identical on both platforms. Installing them with the app means one setup brings
# up an environment where the bundled tests run green with no second install step.
httpx==0.28.1
httpx2==2.5.0
